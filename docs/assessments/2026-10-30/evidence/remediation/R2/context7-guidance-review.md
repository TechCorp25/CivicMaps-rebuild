## Applied guidance and inspected code

- **Express 5 async errors and error middleware.** The official migration and error-handling guidance says rejected promises and thrown errors from returned async handlers are forwarded to error middleware, which has the four-argument `(err, req, res, next)` signature and follows ordinary routes. `services/api/app.mjs` uses async route handlers and places a four-argument error handler after API/static/404 routes (around lines 820–852). Its response is generic for 5xx while server logging follows the existing behavior documented in the R2 operational limits. The guidance matches the installed Express 5 major and inspected usage; no defect was confirmed.
- **React effect lifecycle.** The React guidance requires effects that synchronize external state to clean up symmetrically before reruns/unmount and notes the extra development setup/cleanup cycle. `apps/commandmaps/src/RequestComposer.tsx` opens a dialog in an effect and closes it/restores focus in cleanup; the dependency-based destination effect declares its inputs. Request/activation components use `AbortController` and cleanup or generation checks for asynchronous work, including `apps/commandmaps/src/main.tsx` and `Activation.tsx`. The inspected lifecycle usage is consistent with the documented contract. Because documentation is for 19.2.7/current React docs and installed React is 19.2.0, this is a contract-level review, not a patch identity claim.
- **node-postgres transactions and pooling.** Official transaction guidance requires every statement in a transaction to use the same checked-out client and requires releasing it on completion. `services/api/database.mjs` obtains a client with `pool.connect()`, performs `BEGIN`, callback queries and `COMMIT` on that client, attempts `ROLLBACK` on failure, and releases in `finally`; it destroys/discards the client when a transport/rollback failure requires it. Pool sizes/timeouts are explicit. The inspected pattern matches the docs. The resolver did not offer exact versioned documentation, so no 8.20.0-specific behavior is inferred.
- **Playwright actionability, assertions and context isolation.** Version-pinned guidance says locator actions wait for required actionability checks, web-first expectations retry until success/timeout, and browser contexts isolate cookies/storage. The browser suites use locator-based actions and retrying `expect` assertions, and create explicit contexts where tenant/session isolation is under test (for example `tests/browser-routing.mjs` and `tests/browser-activation.mjs`). Existing R2 evidence has four sequential passing suites; this source-guidance review does not rerun them.
- **Vite 6 dev-server options.** Vite 6 guidance documents the default allowed-host behavior, warns that `server.allowedHosts: true` permits DNS-rebinding access, and describes `server.fs.allow` as widening files available through `/@fs/`, with `server.fs.strict` and the sensitive-file deny list enabled by default. App configs widen `fs.allow` to the repository root for shared source; they do not set `allowedHosts: true`. Their `dev` scripts invoke the root launcher with `--host 127.0.0.1`, use fixed ports and `strictPort: true`, and proxy `/api` to loopback. `scripts/vite.mjs` forwards CLI args to the pinned Vite binary. This is consistent with the documented local-development intent. The observation is based on Vite 6 guidance, not a patch-specific 6.4.5 security review or exploit reproduction.
