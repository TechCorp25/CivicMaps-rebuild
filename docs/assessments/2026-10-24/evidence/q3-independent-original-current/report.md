## Findings

### F1 — High: invalid success bodies bypass uncertain-write reconciliation

Locations: apps/shared/api-transport.mjs:85; apps/commandmaps/src/main.tsx:731 and :828; action enabling at :1253 and adjacent controls.

The transport correctly reports empty/malformed successful responses as ApiError(status=200, kind='invalid-response'). Both action error classifiers treat every ApiError below 500 except 409 as rejected, including this invalid success response. Only uncertain disables actions and exposes the server-state/history reconciliation flow.

Independent reproduction, for each of empty body, {"unfinished": and &lt;html&gt;upstream&lt;/html&gt;:

1. Log in as the synthetic Alpha dispatcher and create/select a new request at version 1.
2. Intercept its assignment POST; execute route.fetch() to commit the real server write, then fulfill HTTP 200 with the selected invalid body.
3. Observe server GET at version 2 while the UI still labels version 1 as server-confirmed, displays Unassigned, enables Assign request and has zero “Check server state and history” controls.

The generic error is safely displayed, but the response uncertainty has been misclassified. Retaining the key internally does not restore reconciliation or prevent another action from the stale detail. This violates acceptance for malformed/empty bodies, committed lost-response recovery and no stale actionable detail. The same classifier is present in retry handling, although the fresh browser reproduction exercised initial assignment.

Reproduction: from the pinned checkout, source the supplied environment and run node ../audit-invalid-write.mjs. The script exits 0 after asserting the defective state; it is a diagnostic reproduction, not an acceptance pass. Fix both classifiers to recognise invalid successful responses as uncertain, preserve the original retry key and require reconciliation before further action. Add executable product regression coverage for these body forms after a real server commit.

### F2 — Medium: obsolete manual history retry can clear a newer live view/session

Location: apps/commandmaps/src/main.tsx:1339 through the retry callbacks at :1349, :1352, :1364 and :1369.

Manual “Retry history” neither passes a lifecycle cancellation signal nor captures/compares a history/selection request generation. Its callbacks compare only scope generation and the selected ID. Those values match again after A → B → A even though the original retry belongs to an obsolete selection.

Independent controlled reproduction:

1. Make A's first history request return 503; click Retry history and hold that retry response.
2. Select B, then A again. Allow A's new history read to succeed; assert fresh history is displayed and the actual session endpoint returns 200.
3. Release the held obsolete retry with HTML 401.
4. The UI returns to Sign in even though the actual session endpoint still returns 200. The old retry has cleared the newer live state.

Raw evidence records three A history reads and session status 200 both before and after stale release. This is a stale outcome after selection changes, not actual session expiry. The same missing generation guard also permits obsolete successful history to replace newer history, though that alternate outcome was not separately executed.

Reproduction: node ../audit-history-aba.mjs under the supplied environment. Fix manual history retries to participate in the same cancellation/generation lifecycle as selection history reads; guard success and error outcomes, including 401. Add A → B → A regression coverage.
