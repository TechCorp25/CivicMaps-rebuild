# Municipality service routing (F06)

F06 uses the [development hostname standard](../civicmaps-naming-pack/DEVELOPMENT-HOSTNAMING-STANDARD.md). Platform and Alpha/Beta CommandMAPS have separate HTTPS origins beneath `dev.civicmaps.com.au`, delegated from VentraIP to Route 53. Reserved EnforcementMAPS/reporting names do not deploy those scaffold apps. Council administrator activation remains F07; routing never marks a municipality Active.

## Application boundary

Migration 008 adds an explicit host manifest, immutable-context/resource references, version, state, lease, safe probe result and event history. Existing sessions gain nullable route/version columns; migration and seed replay preserve existing records. Local development keeps its explicit loopback mode; an unrecognised routing mode fails closed. Deployed API mode must be `CIVICMAPS_ROUTING_MODE=ingress` with distinct private ingress and probe tokens of at least 32 characters. Generate these on the runtime; never commit or publish them.

Caddy accepts the three explicit hosts, rejects client Forwarded/X-Forwarded-Host/X-Civicmaps-Ingress headers and forged X-Forwarded-Proto values, and preserves the authority for backend validation. A supplied HTTPS scheme value is allowed for the execution environment proxy, then overwritten by Caddy; it is never used as authority. TLS SNI and Host must agree. The backend listens only on loopback, checks the ingress token and peer, rejects duplicate/ambiguous authority and permits only canonical registered hosts. DNS case is canonicalised; ports, trailing dots and other authority forms fail closed. Unknown authorities have no application route. Caddy's management API is disabled.

Council authentication requires the host's authorised context before issuing a session. Every subsequent session must match the manifest ID/version, and context selection must agree with the route. Cookies are Secure, HttpOnly, SameSite Strict and host-only in ingress mode. Origin/CSRF checks remain active; same-site sibling domains do not bypass the exact origin check. Platform and council paths remain separate. Manually copying a cookie to another host is rejected server-side.

A council route requires its explicit context/resource mapping, current unrevoked/effective binding, successful F05 job, schema version 2 and enabled resource. The private readiness probe checks the built HTML entry, opens a real F05 runtime TLS database connection and checks the data table. It returns only manifest/context identifiers. Normal access requires state ready and a result less than five minutes old. The routing worker rechecks after 60 seconds, with a 15-second fetch timeout, no redirects and normal public TLS verification. It holds a 60-second fenced lease. A failed probe records a generic error and requires operator retry; repeated worker crashes exhaust the attempt budget. Rechecks retain ready access while the last successful result is fresh.

`GET /api/platform/municipalities/:id/routes` and detail responses expose safe routing status. CSRF-protected retry/withdraw actions require the current route version and an authenticated platform operator. They increment version, invalidate old sessions and record the actor/event. Manifest ownership/context/hostname changes require the trusted structural writer; those actions cannot create a user grant. UI shows ready/pending/failed/withdrawn and verification expiry separately from data provisioning and administrator activation.

## Deployed development runtime

The deployed [CloudFormation template](../../infrastructure/f06/aws-development.json) creates a dedicated Sydney t3.micro runtime, 16 GiB encrypted gp3 disk, IMDSv2, standard CPU credits, static IPv4 and three exact DNS A records in the existing development zone. Only ports 80/443 are inbound; SSH/API/PostgreSQL are not public. SSM provides management. The existing private F05 database accepts connections from the new runtime security group. The privileged F05 acceptance runner stays stopped.

The runtime IAM role reads only the two synthetic F05 credential secrets and F06 release artefacts and assumes a separate two-namespace storage role. Each request still intersects storage access with the single-municipality session policy. It cannot read the F05 master secret or create resources. The master ARN in configuration is a reference needed by the existing target validator; it grants no permission. The EC2 role and control-plane process remain trusted brokers across the two synthetic councils.

Caddy 2.10.2 obtains and renews exact-host public ACME certificates. This avoids an additional ALB or paid exportable certificate. HTTP serves approved-host HTTPS redirects and ACME validation only. The Node API serves the two built web apps and same-origin API. Its dedicated control database lives on encrypted local EBS, loopback only, with SCRAM authentication. The API's control-plane login has BYPASSRLS to perform the existing authentication/broker queries, but has no superuser/database/role-creation powers; operational callbacks explicitly SET LOCAL ROLE to the existing restricted council role. Migration 009 provides narrow void-returning SECURITY DEFINER authentication/context row-lock helpers because PostgreSQL row locks require UPDATE privileges. PUBLIC execution is revoked and only the trusted broker receives execution; identity tables do not gain broad UPDATE grants. This is a development broker boundary, not protection from a compromised broker or a production deployment.

The bootstrap generates a private acceptance password instead of the repository's public local password. It preserves it and the control database across redeploys, seeds synthetic users only and imports the two exact retained F05 resource references. New registrations are paused. No first council administrator is activated. Keep `/etc/civicmaps/runtime.env` private; systemd reads it as root for the unprivileged services. Do not print it or raw provider errors. Application readiness is not a tested production availability/recovery commitment.

## F06Q reliability update

Migration 011 adds a durable `next_attempt_at`. A probe error immediately removes access and schedules the next attempt after 10 seconds, then 30 seconds; the ten-second worker tick can add up to ten seconds. Three unsuccessful claims exhaust the budget and leave the route failed. An expired worker lease consumes the same budget. Successful reconciliation resets attempts; the existing 60-second recheck and five-minute verification lifetime remain. Worker completion checks the lease, deadline and route version. Failed and withdrawn routes are never automatically selected. Explicit retry increments the version and invalidates prior sessions; withdrawal cancels any scheduled retry. Events record scheduled retry, terminal failure, success and operator action without raw provider output.

For terminal **Platform** failure, the UI cannot authenticate while routing is unavailable. Use authorised SSM on the existing runtime; obtain the exact current Platform route version using OS postgres peer access, inspect the owned ingress, then run:

```sh
cd /opt/civicmaps
CIVICMAPS_DATABASE_URL='postgresql://postgres@localhost/civicmaps_f06?host=/var/run/postgresql' \
  runuser -u postgres --preserve-environment -- \
  /opt/civicmaps-node/bin/node scripts/recover-platform-route.mjs CURRENT_VERSION
```

The command requires OS postgres and a privileged database operator, locks only the canonical Platform route in terminal failed state and rejects a stale version or withdrawal. It increments version, clears the exhausted budget and records `out-of-band:ssm-postgres` in route history; retain the SSM command ID for the human audit trail. It cannot create ownership, change hostname/context or publish readiness. The worker must perform a successful probe before public access resumes. Council route recovery remains the authenticated, CSRF-protected Platform action. A DB owner is used for this explicit maintenance capability, not as a substitute for application-role acceptance tests.

Caddy overwrites `X-Civicmaps-Client-Ip` with its direct socket peer address. The API consumes exactly one valid IP only after verifying the loopback peer and private ingress token. Raw `X-Forwarded-For` is never a sign-in key, and Express `trust proxy` remains disabled. Address spellings are canonicalised, including IPv4-mapped loopback. Each canonical service hostname has separate client and normalised-identity limits: at most 20 admitted attempts per minute for either key. Changing clients cannot bypass the identity limit; changing identities cannot bypass the client limit. Identity keys are hashed in memory; buckets expire after a minute, and capacity exhaustion fails closed. This store is appropriate to the approved single API process; a future multi-process deployment requires a shared limiter. Users behind the same NAT or execution proxy share that direct peer client key. Adding a CDN requires a separately authenticated upstream contract.

Settled detail views poll every 15 seconds, active work every two seconds, and each request times out after ten seconds. One effect owns reads, schedules the next poll after completion, and aborts on navigation, refresh or logout. Routing expiry updates on a one-second timer even during an in-flight read. A failed refresh shows status unavailable alongside the last verification time; the next successful poll clears the refresh error. `/api/health` reports `mode: ingress` or `local`, with a separate `data: synthetic` marker. It exposes no tokens, database addresses or credential references.
