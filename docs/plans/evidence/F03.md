Author: Codex (agent). Base main `8954d46` (merged F02Q). Tested implementation: `4c7626194e25b1b5d33c073a24b37d6f21d44f8c`. Implementation extends the existing preparation branch `codex/civicmaps-f03-preparation` and PR #9 as explicitly requested by the owner.

## Delivered behaviour

Migration 004 adds versioned municipality bindings, effective user grants and persisted structural change history. Council operations resolve an explicit permitted context before using transaction-local RLS. One valid binding is the default; missing or ambiguous selection, forged selectors, future/expired periods and revocations deny access. Platform sessions remain separate.

The API exposes `GET /api/auth/contexts` for permitted selectors and accepts `X-CivicMAPS-Context` on operational/session requests. Existing single-context clients continue to work. A synthetic shared-service dispatcher can operate in Alpha and an explicit Beta-jurisdiction association with the same organisation. Officers require grants in the selected context; home scope fields do not implicitly authorise another realm.

Requests retain immutable origin and capture binding/version. Historical records preserve their existing data and NULL capture provenance. Receipt responses are restricted to the exact context; keys in different associations are independent. Earlier-version keys in the same association and legacy keys without context provenance produce 409 without persisting a duplicate write. Expired/revoked authority denies replay before receipt lookup.

Resolution uses row share locks and database wall-clock time after acquisition. Structural revocation waits for a resolved transaction; a committed revocation wins against a waiting resolver. Existing authorised transactions may finish across a time boundary. Bound scopes and dates are immutable; revocation and replacement preserve history.

## Review, compatibility and limits

See the [context contract](../../development/operating-context.md) for field semantics, API behaviour, structural authoring and concurrency policy. PostgreSQL 15 share-lock semantics were checked against official docs through Context7. Database-time evaluation avoids transaction-start timestamps and JavaScript timestamp truncation at expiry boundaries.

Authoring is currently through the privileged database/migration writer, audited by database identity. Application roles cannot author bindings or grants. Operator-facing authoring, per-realm roles and a web context chooser are subsequent work; this phase supplies API context selection. New registry onboarding alone still does not provision a realm or activate an admin. No provider, DNS, portal or payment changes.

An old API binary is unsafe/incompatible with the new authority contract and capture requirement. Keep resolver and migration together; stop affected writes or revoke access while correcting a release. Do not silently fall back to old user scope fields. A destructive down-migration or restoring an old database needs its own reviewed recovery plan; none was performed here.

## Gotchas resolved

A BEFORE INSERT audit trigger fires even for an `ON CONFLICT DO NOTHING` seed attempt. The populated-upgrade repeat-seed test caught false audit rows. Audit recording now uses AFTER triggers, and the test passes with unchanged audit counts.

Legacy receipts lack context provenance. Assigning them guessed scope or permitting their keys to be reused could disclose data or duplicate writes. Preserve the receipts and reject those keys with an actor-scoped guard.

Exact binding version changes also require retry protection: lineage-wide uniqueness rolls back attempts with an earlier version's key, while exact-binding RLS keeps the older response hidden. The replacement-version test verifies no duplicate request persists.

Evaluate expiry after waiting for structural locks with PostgreSQL clock time, rather than a transaction-start timestamp or truncated JS Date. Preserve the one-environment-per-test-process rule when building populated-upgrade fixtures.
