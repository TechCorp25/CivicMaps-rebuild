## Required corrections and implementation details

1. **Correct token/history and grant terminology.** The governing reassessment says D02 “deletes sessions/tokens”, and acceptance lists “zero sessions/tokens”. Migration 012 deletes sessions but updates outstanding activation rows' `revoked_at`; redeemed/revoked token rows remain as history. Require zero sessions and zero *usable outstanding activation tokens*, preserve token/event rows, and do not add token deletion. Migration 004 has no standalone grant ID: retain the `(user_id,binding_id)` key plus `operating_context_changes` before/after evidence. Its immutability trigger prevents unrevoking and its primary key prevents a second grant to that same binding; do not introduce grant replacement/regrant functionality here.

2. **Specify manifest-to-migration execution and admission ordering.** `migrate.mjs` currently executes SQL files in one advisory-locked transaction; PostgreSQL does not consume the proposed JSON by itself. Load/validate the explicit manifest in the runner and stage it transactionally for 014, or specify an equivalent single-source mechanism. Cover fresh empty installs (migrate precedes seed), existing pre-014 fixtures, and pre-004 upgrade fixtures whose users exist before municipalities/bindings are seeded. Explicit municipality prerequisite creation or a bounded fixture setup must precede owner foreign keys; never derive the missing council from home fields. Seed order must be municipalities/users, owners, bindings/grants. Validate D02 user/binding/municipality agreement, duplicate manifest entries, unknown users and all unclassified active grant relationships before enforcement. Stop all API admission during migration; the migration advisory lock alone does not stop ordinary application writes. Abort the whole migration on unknown ownership, with no partial session-revocation fallback hidden in that aborted transaction.

3. **Resolve legacy-session and login-error contradictions.** The narrative permits unambiguously mapped existing sessions to be backfilled and retained, while acceptance says stale pre-migration sessions are denied. Require denial of *unbound, mismatched, expired, disabled or wrong-route* legacy sessions; explicitly mapped valid sessions may remain council-bound. For `shared@alpha`, revoke a pre-existing Beta-routed session or deny it on every path, including `/auth/contexts`; retained local/Alpha sessions must be Alpha-only. Existing `routeContext` throws 403 “Service access is not permitted” after a globally successful password lookup, unlike login's generic 401. Normalize wrong-council login failure within the current unique-email slice; reserve missing-audience/duplicate-identifier behavior for the later audience-scoped API. Review login's unconditional deletion of the incoming cookie's session so replacing a Beta login cannot inadvertently revoke a separate Alpha session; use separate council cookie jars in independence tests.

4. **Keep database claims exact.** Explicitly cover insert/update immutability of the session's `(user_id,council)` pair and DB-authoritative owner checks on direct resolver paths; `permittedContexts` currently does not itself recheck active status. Preserve the user/session and binding/grant lock ordering in 009/012 against disable/revoke races. Migration 014 should explicitly maintain or strengthen `valid_operating_context()` from 005 for the owner invariant, and grant runtime only necessary owner reads/helper execution. App roles currently cannot write grants at all: their same-council insert should remain permission-denied; positive grant writes belong to the authorized synthetic writer/D02 path. These checks cannot authenticate an arbitrary actor ID supplied by a compromised BYPASSRLS broker. No new generic owner/grant endpoint is required.

5. **Make exact test compatibility scope explicit.** Add `tests/pack-entitlements-upgrade.test.mjs`, `tests/admin-activation-upgrade.test.mjs`, and `tests/service-routing-upgrade.test.mjs` to the affected-file review. They construct historical sessions; the pack-upgrade fixture also creates principal `...0099` without a D02 owner link. Give positive historical fixtures explicit test-only ownership, never an inferred production mapping. `context-migration.test.mjs` currently expects an unknown principal to migrate and authenticate, then fail context resolution; split that into a successful explicitly mapped upgrade and a separate preflight-failure case. Update its migration count of 13. Dynamic principal helpers need explicit owner records. Test fresh install separately from pre-014 retirement: a fresh corrected seed should not invent a historical Beta grant merely to revoke it. Require preserved pre-existing Beta records/history in the upgrade fixture and positive same-council multi-context isolation/idempotency coverage replacing the old shared-council success test.

6. **Correct normalized-email and deferred recovery wording.** Foundation `email text UNIQUE` is globally unique but case-sensitive; normalized uniqueness is not a database invariant. Say that current API paths normalize and exact stored-email duplicates are rejected, or explicitly specify additional validation without claiming it already exists. Do not enable duplicates here. The governing actor table still includes “recovery” under generic independent council approvers, conflicting with its separate recovery-custodian requirement and the first review's correction. Remove that generic authority; this does not block ownership implementation because recovery is excluded.

## Release/recovery boundary and conclusion

“Old application code cannot run” should mean **must not be admitted**, not an asserted technical compatibility guarantee: old reads can still execute against added schema and existing sessions. Keep operation closed through a compatible forward repair, and make that admission control an explicit synthetic rollout prerequisite. A schema column alone cannot enforce release selection, nor can this slice discover revocations erased by a whole-database restore. No restore procedure or external immutable evidence service is being implemented.

The listed application/migration files are adequate with the specified upgrade-test additions and narrowly scoped 014 helper replacements. No UI, new authority endpoints, production ownership algorithm or infrastructure redesign is necessary. The remaining points are implementation choices and source corrections, not unresolved Q01–Q05 policy. They should be incorporated into the contract and implementation acceptance criteria; the owner should not be asked to repeat signed choices. This review supports starting the bounded synthetic implementation, with actual success to be established by subsequent implementation review and authorized tests.
