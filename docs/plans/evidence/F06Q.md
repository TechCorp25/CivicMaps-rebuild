## Review follow-up — disposable restore cleanup

The [follow-up review finding](https://github.com/TechCorp25/CivicMaps-rebuild/pull/16#discussion_r4302266471) on `617757e` is validated. A failed row-count assertion or interruption after `createdb` left the deterministic verification database behind, and the outer service-recovery handler did not remove it. Retrying the same source revision could then fail at database creation.

The release now calls `infrastructure/f06/verify-backup.sh` as the database operator. It uses a unique verification name for each invocation and removes only its successfully created database on exit, including restore/assertion failures and catchable interruption. Failed creation does not authorise deletion; cleanup failure fails the helper, allowing the outer release handler to restore services. An uncatchable termination cannot run traps, but a unique name prevents its remnant from blocking a later retry; existing databases are never adopted or removed.

`tests/release-backup.test.mjs` uses real disposable PostgreSQL databases and verifies successful cleanup, an invalid restore, an incorrect restored route count, SIGTERM, successful retry with the same revision, failed creation without a drop, and preservation of a pre-existing database. Shell syntax checks and `npm run check` passed with **67/67 integration tests**, lint, formatting, both typechecks/builds. These maintenance changes are not yet deployed and do not extend the historical live-release evidence below.

## Corrected findings

- **A1 — recoverable routing:** migration 011 persists retry deadlines. Failed probes immediately fail closed, back off 10/30 seconds and exhaust three claims. Successful reconciliation resets attempts. Restarts, repeated crashes during initial verification **and ready-route rechecks**, concurrent workers, stale completion and withdrawal are fenced. Events distinguish scheduled retries, terminal failures and operator actions. Terminal Platform recovery requires the authenticated OS/DB operator and current version; it cannot revive withdrawal or publish readiness. A new real TLS probe must succeed. Council actions retain authenticated operator/CSRF checks.
- **A2 — sign-in isolation:** Caddy overwrites the client-IP header with its actual socket peer. The backend accepts exactly one valid canonical address only after private-token and loopback-peer authentication. Per-host client and normalised-identity limits each admit at most 20 attempts/minute. Independent clients and Alpha/Beta/Platform have separate client buckets; changing addresses cannot evade one identity's limit. Raw forwarding headers never set the client key. No public authentication-load test was performed.
- **A3 — current status:** detail reads remain serial, use ten-second timeouts, poll settled routes every 15 seconds and active work every two seconds, recover after refresh failure and abort on navigation/logout. Mounted readiness expires without clicks; a failed refresh shows unavailable rather than a current-ready claim.
- **A4 — release alignment:** actual old source/schema were inspected, migration 010/011 applied through a private backup/restore checkpoint, and exact tested source/built apps deployed to the existing runtime. Application rollback and return preserved data, sessions, ownership, versions and private configuration. Maintenance now waits for authenticated private HTTPS readiness before starting the worker.
- **A5 — truthful health:** `/api/health` separates `mode: ingress`/`local` from `data: synthetic`, without credentials or internal connection details.
