## Actor and action boundaries observed

| Actor | Current actions evidenced | Data visibility and authority limit |
| --- | --- | --- |
| CivicMAPS platform operator | Authenticate to the Platform surface; list/read municipality configuration, pack workload, recent platform audit, provisioning status and service routes; register a municipality and designated first-admin contact; change feature packs; retry/reconcile jobs; retry or withdraw a municipality-scoped service route; issue or disable the designated first admin through explicit flows. Business control-plane requests use the authenticated operator/session and route-bound wrapper; mutations additionally use CSRF and idempotency, with actor-attributed audit on control actions. Route controls require the current route version. Retry resets a route to pending; withdrawal sets it withdrawn. Only a ready and recently checked route passes middleware, and sessions bind to route ID/version, so these controls can interrupt service and invalidate prior route-bound sessions. Platform login/logout have separate handling and are not all covered by the mutation wrapper. This route control is separate from unapproved F09 municipality suspension. See [platform routes](../../../services/api/platform.mjs), [routing controls](../../../services/api/routing.mjs), [activation routes](../../../services/api/admin-activation.mjs), [migrations 003/008/012/013](../../../services/api/migrations/). | The platform SQL role is granted control-plane tables and is not granted direct `SELECT` on council `service_requests` or `users`. The operator UI/API does not provide an arbitrary council-record reader. Route retry/withdraw changes service routing state, not request records. This does not establish provider non-access: the runtime, database owner, privileged broker and infrastructure administrators remain separate trusted actors with broader technical powers. |
| Council `ADMIN` profile | Sign in and see own profile and authorised context. Account activation/disable is performed through explicit Platform flows. | `ADMIN` is excluded from operational request, personnel, audit and resource actions by current application checks/RLS. This is not the promised full council self-administration surface: no implemented council interface for staff lifecycle, delegated roles, branches or local configuration was found. |
| Council dispatcher | In an effective council operating context, read scoped requests/audit and, when the pack is enabled, read the officer directory and resource status; create a service request, assign an officer and close a request where capabilities allow. | Reads/writes are scoped by tenant, jurisdiction, data plane, organisation, branch, context, session, feature entitlement and role checks. The present control database remains shared; row-level and application checks do not equal a dedicated physical tenant store. |
| Council officer | Read scoped requests/audit and, when the pack is enabled, the officer directory and resource status; read assigned requests and, when permitted by state and entitlement, acknowledge and record attendance. | Assignment and current context constrain visibility. No live officer-location or device-tracking action is implemented. |
| Council supervisor | Read scoped requests/audit and, when the pack is enabled, the officer directory and resource status; operational mutations are not granted. | Mutation routes reject this role. This is a partial role model, not a complete council RBAC design. |
| API runtime | The API process resolves council identity/context and performs application requests. Its configured `civicmaps_f06_runtime` login has `BYPASSRLS`, `SELECT` on all control-database tables, sequence access and membership in both `civicmaps_local_app` and `civicmaps_platform_app`; runtime resource paths can retrieve plaintext credentials needed for work. See [runtime role setup](../../../infrastructure/f06/configure-control-login.py) and [resource resolver](../../../services/api/data-resources.mjs). | This login has cross-council technical read capability and broader control-plane capability beyond the narrower application-role grants. This is an observed development trust boundary and a material G03 issue, not evidence of an unauthorized access event. It must not be described as provider non-access. |
| Provisioning worker | Processes provisioning jobs, checkpoints effects and appends platform audit under its designed control-plane role. See [worker contract](../../development/provisioning-jobs.md) and [provisioning implementation](../../../services/api/provisioning.mjs). | The provisioning SQL role has separate grants and restrictions; tests deny user/admin reads, municipality activation and job deletion. This does not remove the host/runtime operator boundary. |
| Routing worker | Runs route verification, leases route state and appends route events. The service unit uses the same `civicmaps` OS identity and runtime environment as the API. See [routing worker](../../../services/api/routing-worker.mjs), [routing unit](../../../infrastructure/f06/civicmaps-routing.service) and [API unit](../../../infrastructure/f06/civicmaps-api.service). | Route transitions affect service availability. Same OS identity/environment means the SQL/application separation does not establish independent host credentials between API and routing worker. Route changes are not request-record operations. |
| AWS, database and host administrators / support | Infrastructure and support privileges are outside council UI roles. SSM-managed host access and privileged provisioning/runtime roles were observed. | These are high-trust, potentially cross-council actors. Just-in-time approval, support access, break-glass, customer visibility and an absolute provider non-access model remain unresolved. |
| Public reporters, complainants and other end users | No public/service-report intake route or public identity flow is implemented in the reviewed operational API. | Public reporting is an owner-required future class, not an established current source flow. A report entered by a dispatcher must not be represented as public self-service intake. |

Platform operator status therefore does not itself grant council operational permissions in the application role model. Council authority is also not yet self-administered end to end.

### Council self-administration decision set (proposed, unapproved)

| Decision | Bounded options for accountable review | Consequence / dependency |
| --- | --- | --- |
| Staff lifecycle and operational-role grants | (A) one council administrator manages joiner/mover/leaver and roles; (B) delegated role-scoped administrators with optional dual approval for high-impact grants; (C) council IdP/SCIM is authoritative, with CivicMAPS mapping only approved groups. | A is simpler but concentrates authority; B adds separation and approval complexity; C shifts lifecycle to customer identity governance and needs a defined sync/revocation-failure policy. All require direct API authorization, revocation and audit tests. No option is selected. |
| Branch/context and configuration administration | (A) council administrator manages only pre-approved branches/settings; (B) separate branch administrator with council-level approval for context creation/binding changes. | A broadens a single council role; B reduces privilege but requires approval and recovery semantics. Any change must preserve tenant/context scope and avoid silently expanding existing grants. No option is selected. |
| Licensed feature activation | (A) operator sets commercial ceiling, council administrator activates within it; (B) operator changes ceiling and council requests activation, with explicit operator confirmation; (C) council requests and operator/council dual approval activates. | A provides local autonomy within contracted entitlement; B adds operator dependency; C provides stronger two-party control but slows changes. Pack availability must not itself create staff permissions. No option is selected. |
| Administrator cardinality and recovery | (A) one active administrator with audited operator recovery; (B) at least two council administrators with delegated recovery; (C) customer IdP administrators recover accounts under council policy. | A risks single-person lockout and gives support an explicit recovery path; B reduces lockout but changes cardinality/grant semantics; C depends on IdP and fallback policy. Existing F08 Alpha/Beta states are fixed preservation constraints. No option is selected. |
| Authentication, bootstrap and privileged support | Decide MFA/SSO requirements, independent first-admin verification, just-in-time support elevation, emergency access, customer notice/approval, impersonation prohibition/exception, and audit/export. | Bootstrap possession is currently bearer-token based. Extending ADMIN authority would elevate this trust. The choice affects identity, session, support and infrastructure boundaries and needs named owner/customer approval. No choice is inferred from current operator authentication. |
| Role scope, grant escalation and regrant | Decide whether roles attach globally to a user, to a council or to one operating context; whether admins may grant themselves, create another admin or approve their own grants; and how revoked grants are replaced. | Current role is on the user row and context selection replaces scope dimensions while retaining role. Grants use immutable/revocable bindings; revocation is not a routine update/regrant path. See [user schema](../../../services/api/migrations/001-foundation.sql), [context/grant schema](../../../services/api/migrations/004-operating-context.sql) and [context resolution](../../../services/api/operating-context.mjs). Cross-council escalation, rehire and grant replacement require explicit semantics and preservation tests. |
| Attribution and retained-record custody | Define human/service principal, approver and target attribution for every admin action; identify who may review/export records after staff departure, assignment change, context closure, pack disable or route withdrawal. | Current context history records the database actor; it does not itself provide full customer-facing approver/target attribution. Officer record visibility follows current assignment; pack disable and route withdrawal have different effects and neither defines records custody or exit/export. Define restore/revocation persistence and recovery before implementation. |

**Accountable decision owners:** CivicMAPS owner for product/platform authority; each council's designated security/privacy/service owner for local administration and staff policy; operator security/architecture owner for runtime/support controls. Named customer owners and decisions are not yet available. Production and legal acceptance remain separate from permission to continue independent development.

Every workflow/class above still requires customer-specific applicability and contract validation. This table does not assign one identical rule to all councils.
