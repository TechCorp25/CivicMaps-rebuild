## Actor and action boundaries observed

| Actor | Current actions evidenced | Data visibility and authority limit |
| --- | --- | --- |
| CivicMAPS platform operator | Authenticate to the Platform surface; list/read municipality configuration, pack workload, recent platform audit, provisioning status and service routes; register a municipality and designated first-admin contact; change feature packs; retry/reconcile jobs; retry or withdraw a municipality-scoped service route; issue or disable the designated first admin through explicit flows. Route controls require the current route version and append `service_route_events` with the operator actor ID. Retry resets the route to pending; withdrawal sets it withdrawn. Only a ready and recently checked route passes middleware, and sessions are bound to route ID/version, so these controls can interrupt service and invalidate prior route-bound sessions. This existing route control is separate from any unapproved F09 municipality-suspension policy. See [platform routes](../../../services/api/platform.mjs), [routing controls](../../../services/api/routing.mjs), [activation routes](../../../services/api/admin-activation.mjs), [migrations 003/008/012/013](../../../services/api/migrations/). | The platform SQL role is granted control-plane tables and is not granted direct `SELECT` on council `service_requests` or `users`. The operator UI/API does not provide an arbitrary council-record reader. Route retry/withdraw changes service routing state, not request records. This does not establish provider non-access: the runtime, database owner, privileged broker and infrastructure administrators remain separate trusted actors with broader technical powers. |
| Council `ADMIN` profile | Sign in and see own profile and authorised context. Account activation/disable is performed through explicit Platform flows. | `ADMIN` is excluded from operational request, personnel, audit and resource actions by current application checks/RLS. This is not the promised full council self-administration surface: no implemented council interface for staff lifecycle, delegated roles, branches or local configuration was found. |
| Council dispatcher | In an effective council operating context with required capability, list a bounded request queue, create a service request, assign an officer and close a request. | Reads/writes are scoped by tenant, jurisdiction, data plane, organisation, branch, context, session, feature entitlement and role checks. The present control database remains shared; row-level and application checks do not equal a dedicated physical tenant store. |
| Council officer | Read assigned requests and, when permitted by state and entitlement, acknowledge and record attendance. | Assignment and current context constrain visibility. No live officer-location or device-tracking action is implemented. |
| Council supervisor | Read-only scoped request and audit review. | Mutation routes reject this role. This is a partial role model, not a complete council RBAC design. |
| Provisioning worker / service runtime | Worker processes jobs, checkpoints effects and appends platform audit; the API resource-status path resolves a council resource/context and probes it. See [worker contract](../../development/provisioning-jobs.md) and [resource contract](../../development/data-resources.md). | Distinct SQL roles and bounded provider permissions exist in the development design. The service runtime/broker can use credentials and retrieve plaintext needed for its work. These controls do not prevent a privileged operator from changing code or accessing runtime/host/DB privileges. |
| AWS, database and host administrators / support | Infrastructure and support privileges are outside council UI roles. SSM-managed host access and privileged provisioning/runtime roles were observed. | These are high-trust, potentially cross-council actors. Just-in-time approval, support access, break-glass, customer visibility and an absolute provider non-access model remain unresolved. |
| Public reporters, complainants and other end users | No public/service-report intake route or public identity flow is implemented in the reviewed operational API. | Public reporting is an owner-required future class, not an established current source flow. A report entered by a dispatcher must not be represented as public self-service intake. |

Platform operator status therefore does not itself grant council operational permissions in the application role model. Council authority is also not yet self-administered end to end.

## National jurisdiction crosswalk

The existing [national obligations register](../national-governance-obligations-register.md) is the source for the following enacted-law and public-record starting points. Every workflow/class above still requires customer-specific applicability and contract validation. This table does not assign one identical rule to all councils.

| Obligation source class | Current treatment |
| --- | --- |
| Enacted legislation and binding instruments | The eight jurisdiction rows name verified starting points from the national register. Whether a provision applies to a specific council, operator, record, recipient or workflow remains a legal/customer determination. |
| Contractual and procurement requirements | Council/provider contracts, data-processing terms, security schedules, residency/incident clauses and customer policy have not been reviewed for a named customer; record them separately from legislation. |
| Government security/records guidance | ASD, PSPF, Essential Eight/Essentials, cloud-assurance and state records guidance are identified in the national register. Applicability, version and assurance boundary depend on customer policy and contract; guidance is not silently promoted to a universal council statute. |
| Proposed CivicMAPS controls | GOV requirements and work packages are engineering proposals/owner requirements. They do not themselves create legal permission, statutory power, retention period or production approval. |

| Jurisdiction | Verified starting points in national register | Open decision for each implemented/future class |
| --- | --- | --- |
| New South Wales | PPIP Act 1998; HRIP Act 2002 where applicable; State Records Act 1998; local-council breach scheme guidance. | Named council, health/sensitive eligibility, incident controller, records authority and supplier duties. |
| Victoria | PDP Act 2014/IPPs; Health Records Act 2001 where applicable; Public Records Act 1973 and PROV RDAs; interstate transfer consideration. | Council/provider responsibilities, transfer ground for Sydney/interstate processing, class schedule and contracts. |
| Queensland | Information Privacy Act 2009/current QPPs; council MNDB commencement from 1 July 2026; Public Records Act 2023. | Applicable QPP/incident recipient, supplier cooperation and current RDA/trigger for the workflow. |

The register also treats Commonwealth Privacy Act/APP applicability for the private operator, contracts and security guidance separately from council statutes. Relevant ASD/PSPF/Essential Eight/cloud guidance is not automatically an enacted council duty. Infringement, health, surveillance, payment, evidence and breach rules remain workflow-specific legal decisions. No exhaustive compliance claim is made.
