## Behaviour and scope

F11E binds request and history reads to the selected request and active session/context generation. Selection changes, dismissal, context replacement and session loss invalidate delayed results. Detail shows server-confirmed status, version and update time; history has loading, empty, unavailable and retry states. Existing capability-gated actions remain. Action failure is shown for the selected request; rejected/conflict outcomes retain safe drafts. A transport-uncertain write is not replayed automatically: the operator first reconciles server state/history, then may deliberately retry only when the server version still matches the attempted version, with existing idempotency semantics. Conflict refresh does not silently rebase the draft/action. Focus returns to the selected queue row on dismissal.

Each request retains its own unresolved recovery state, so a successful action on another request cannot erase it. Reconciliation updates the visible history only while that request remains selected. An untouched assignment selector follows confirmed server assignments/version changes; user-edited drafts stay intact across conflicts. A deliberate post-reconciliation retry reuses the original idempotency key.

The detail remains an inline, non-modal panel. No server permission, state, schema, identity, deployment, migration, seed or live data changed. Latest-100 remains disclosed. G04 governance findings F-002/F-009/F-011/F-029 remain owned by the separate governance workstream; this implementation does not depend on or duplicate them.

## Codex review findings and response

The established Codex review on PR #27 head `e6dd6cc4e2576e86b72f82929c8e8f81d444d418` completed with three actionable findings:

1. **P1 — refreshed assignment could silently overwrite a concurrent reassignment.** Fixed by syncing pristine assignment drafts on confirmed assignment/version updates while retaining edited drafts; covered with two synthetic, independently scoped alpha officers and refreshes.
2. **P1 — another request's successful action could erase an unresolved uncertain write.** Fixed by storing recovery state per request and retaining the original idempotency key for a deliberate retry; covered by leaving A uncertain, successfully acting on B, returning to A and retrying with exactly the captured original key, with one audit entry.
3. **P2 — A's reconciliation history could replace B's visible history after selection changed.** Fixed by only applying reconciliation history when the same request remains selected; the synthetic browser test delays A history while switching to B and asserts B's history remains visible.

All three findings were validated against current source and existing API version/idempotency behavior. Fixes and focused tests were committed in `a47b7adbafba25f42d65596d604c42c02cf2163d` and pushed to PR #27. The prior review did find issues; no review-ready or advanced-model approval is claimed until hosted CI and a fresh review accept the updated head.
