## Fixed owner direction

- **Q01 B+C:** council central security is primary; documented, capability-qualified branch teams may handle routine staff changes and branch-scoped access approvals; central security resumes branch work when delegation expires or qualification is absent. Elevated/cross-branch changes need independent council-level approval.
- **Q02 C+A:** each council independently owns identity, sessions, status, grants, work and records. One human working for two councils has independent council principals; no cross-council sharing, inheritance, visibility, identity linking/discovery or operational federation. Within each council, grants are scoped to approved branches/contexts.
- **Q03 A:** prefer suitable council SSO; governed CivicMAPS account with MFA is fallback. No IdP/vendor selected.
- **Q04 C+A:** two named active MFA admins plus a separate independently verified recovery custodian. Prompt disablement is not blocked when it leaves fewer than two admins. Recovery requires custodian authorization and bounded audited operator execution; Q07 second operator applies if action is classified high impact. Existing D02 bootstrap tokens gain no recovery powers.
- **Q05 C+A:** independent council authorization of the exact high-impact structural/access change; during initial rollout, bounded operator execution of only that approved change, plus Q07 second-operator approval for privileged high-impact action. Preserve versions, grants, revocations and origins; no automatic cloning or revival.

First-admin activation checks email collisions globally and writes a user plus context grant.

There is a concrete synthetic cross-council case: fixture user `00000000-0000-4000-8000-000000000006`, `shared@alpha.example`, owns Alpha home fields but `data/fixtures/operating-contexts.json` includes the third context with Beta municipality, `organisation-alpha`, and that user in `userIds`. `tests/operating-context.test.mjs` expressly logs that one principal in, uses both Alpha and Beta contexts, and later adds the Alpha officer's Beta grant. This current successful test expectation conflicts with signed Q02. It is synthetic test data and is **not evidence a live shared identity exists**.

The separately required state preservation is not erased by the fixture correction: retain the actual Alpha first-admin as usable and Beta first-admin as disabled with no sessions. D02 disable sets Beta user inactive, deletes sessions, revokes outstanding activation tokens while retaining token/event history, and does not revoke its existing context-grant row. The migration must account for the inactive principal's still-present grant row; it must not claim the row was revoked. It remains non-effective because the principal is inactive, and its owner is Beta. Alpha and Beta first-admin state is checked independently from the `shared@alpha` fixture change.

## Revised Q01–Q05 actor/action boundary

| Actor | In-scope authority | Boundary |
|---|---|---|
| Council central security | Council-level staff lifecycle, define/withdraw branch delegation, routine central administration, independently approve elevated/cross-branch changes. | A council administration permission is separate from operational context role and does not require an enabled pack. No operational/history access by admin label; no cross-council identity visibility; no self-approval of elevation. Exact routine action list and verifier remain dependencies. |
| Qualified delegated branch administrator | Routine staff changes and branch-scoped access approvals only inside a current documented delegation. | Cannot create/widen own delegation, self-elevate, act cross-branch/council, or perform unlisted structural/high-impact action. Central security resumes work when delegation is invalid. Second-level delegation is disallowed for first slice; future exception requires separate design. |
| Independent council approver | Approve an exact scoped grant/structural change or other council authority change when Q01/Q04/Q05 require it. | Not the same human as proposer/subject where self-approval prohibited. Must be a council principal with current scope. Does not replace Q07 second operator. |
| Two council admins | Receive only explicitly designed council administration actions after verification/enrollment; participate in routine lifecycle under Q01. | Existing `ADMIN` remains only profile/context bootstrap. Neither admin gains recovery-custodian powers, operational record access, or self-approval. Actual staff lifecycle endpoints are outside first slice. |
| Separate recovery custodian | Independently authorize a council-specific exceptional recovery. | Cannot execute; must be distinct from both active admins; cannot approve for another council. If unavailable, no bootstrap/operator bypass. |
| Operational officer/dispatcher/supervisor | Existing current operational actions inside one council and explicit context/grant/capability. | No staff administration, council structural changes, recovery or cross-council scope. Existing global `users.role` is an acknowledged limitation: this slice blocks cross-council ownership only and does not claim Q02 per-context role semantics are complete. |
| Routine/privileged operator | Current bounded service work. For Q05, a designated operator may execute only the exact independently council-approved change; privileged action additionally requires independent operator approval under Q07. | No discretion to choose council membership, grants or contexts. Different credentials for same human are not independent. No recovery or emergency exception absent separately approved procedure. |

### Administration and grant scopes

Council administration scope is a typed council-level permission, not a fake/wildcard branch/context grant. Operational role grants remain context-bound. Q01 central security and qualified branch delegation can be modeled later as separate action permissions; do not add generic `manage staff` or administration endpoints in this first slice. Q06 feature activation and Q09 custodian access are separate permissions and must not attach to the `ADMIN` role.

### State and transaction rules for later authority workflows

For future authority work, principals have council-scoped pending/active/disabled/departed states; grants are proposed/approved/active/revoked/replaced and bind a single principal to one council and explicit context/version; approvals bind exact action, subject, target, before/after version and actor. Rehire/replacement requires explicit authority, not reactivation of a revoked grant. Q05 council authorization and Q07 operator approval are separate approvals. At execution, revalidate current principal/delegation/approver status, exact target/version and revocations under a serialized transaction; persist authority change and audit atomically. Replays cannot cause a second effect. If external effects are uncertain, block new authority and reconcile; partial unapproved authority is not an acceptable state. These workflow mechanics are later slices, not implemented by owner-ownership metadata.

## Exact first-slice work contract: synthetic principal ownership enforcement

### Goal and exclusion

Add an immutable one-council owner for every synthetic council principal and enforce that owner at login-session issuance, session authentication, context resolution/routing and context-grant creation. Retire the known Alpha principal's Beta fixture grant without rewriting audit/request origins or copying credentials. This is not council staff administration, per-context roles, duplicate-email support, IdP integration, recovery, Q05 structural execution, dedicated deployment, or production isolation.

### Explicit ownership manifest

**Proposal:** introduce `data/fixtures/council-principal-ownership.json`, containing explicit principal ID and council municipality ID entries for Alpha IDs 1/2/3/6 and Beta IDs 4/5, plus a rule/source for the designated first-admin principal: the municipality relationship in `platform_first_admins` that D02 already binds to that user. Do not derive ownership from `email`, `tenant_id`, `organisation_id`, `jurisdiction_id`, selected context, or the user's display name. The migration preflight must enumerate every existing principal and refuse to start service if a principal lacks exactly one explicit council owner or if the manifest conflicts with existing D02 owner links. Unknown customer/non-synthetic rows are not guessed or auto-migrated.

Each synthetic `users.id` maps to exactly one immutable `municipality_id`; there is no auto-split, account clone, credential/password copy, or replacement grant. **This fixture manifest is not the algorithm for customer/production ownership.** Any real or non-fixture principal without authoritative council ownership must fail closed and block migration/service admission for the affected identity until a council-approved mapping is supplied. Never infer ownership from email, home tenant/organisation/jurisdiction fields, or the currently selected context. The fixture owner map cannot be changed by an API actor or runtime role.

Q02 also governs login behavior when two councils use the same email: authentication must be council-audience scoped and query a local identifier only inside that council's immutable owner namespace. The same email at Council A and Council B represents distinct principals/sessions; a global email lookup must never select one and then try to validate the other council later. Unknown email, wrong password, absent council audience, or an email present only at another council must return the same generic login failure and must not disclose account existence, status, or other councils. A local username may be used instead of email when a council's approved identity lifecycle requires it. This first slice retains current unique synthetic emails and does not add duplicate-email sign-in; it leaves a clear Q03 dependency to implement council-scoped lookup before allowing duplicate email addresses.

### Session and principal independence

A principal's successful login creates a session immutably bound to its sole owner council. Every restored `/auth/session`, context selection, operational route and routed-host path must recheck that owner. A copied Alpha cookie cannot act as a Beta principal or use a Beta context. Disabling a principal invalidates its sessions as today. This slice keeps globally unique synthetic emails; before duplicate email is allowed, council-qualified authentication must require an explicit council audience and query `(council_id, normalized_local_identifier)`, with indistinguishable failures and no cross-council existence lookup. A later Q03 auth slice must support separate principal IDs, credential lifecycle and sessions for the same human, including separate MFA/revocation. No shared SSO session becomes a shared CivicMAPS authorization session.

### Positive and negative acceptance cases

Required tests after implementation; current tests have not been run for this contract.

1. **Positive, same council:** one Alpha-owned principal retains permitted Alpha context(s); valid Alpha session works. A context selector for another context owned by Alpha works only if the explicit grant is valid. Existing same-council context filtering, record isolation and idempotency behavior remain.
2. **Positive, two councils:** distinct Alpha and Beta principal IDs, emails/credentials and owner rows may each authenticate independently; each session sees only its council-owned context(s). One browser/client holding the two distinct session values cannot use either session for the other council. Disable Alpha does not revoke/alter Beta's independent account or session and vice versa.
3. **Positive, more than two councils:** create a synthetic Gamma (third municipality/owner) and at least one additional context. Explicitly owned Alpha/Beta/Gamma principals each authenticate; per-owner context list and route resolution remain correct. This proves owner enforcement is data-driven, not hard-coded to Alpha/Beta.
4. **Known superseded fixture:** `shared@alpha.example` authenticates as Alpha only; `/auth/contexts`, route context, requests, audit and officer actions cannot use Beta binding `...0003`. Its Alpha grant remains. Beta grant row is retained with `revoked_at` and history evidence. No cloned Beta user/password/session/grant is created.
5. **Beta disabled admin preservation:** Beta's initial admin stays inactive, cannot log in, has zero sessions and zero usable outstanding activation tokens; retain revoked/redeemed token rows, and cannot resolve context. Its historical grant row is checked and remains non-effective; do not assert it is revoked unless migration actually and separately authorizes that change. Alpha initial admin remains active and can sign in/use its approved profile/context only.
6. **Direct grant writes:** attempt same-council active grant (allow), cross-council active grant through seed/admin/runtime-controlled route and direct SQL (deny); revoked historical inconsistent grant update remains auditable. Attempts to update/delete owner mapping fail for app/runtime actors.
7. **Session boundary:** use Alpha cookie with Beta context/routed service, altered session-owner value, missing/unknown owner, stale owner mapping and post-disable session. All deny before transaction scope is established. Wrong-council lookup produces generic response without revealing account/council existence.
8. **D02 boundary:** first-admin activation creates owner from the verified activation municipality/binding in the same transaction; token remains 24h, single-use, hashed, exact binding, safe reissue and no plaintext replay. Token can’t assign a different owner. Disable preserves Beta no-session state and does not create recovery.
9. **Legacy/history:** migration preserves row IDs, historical actor IDs, service request origins, audit and mutation receipts. Beta history does not become visible to the retained Alpha principal. No automatic reattribution, record cloning, duplicate identity, password copy, grant cloning or cross-council login.
10. **Concurrency/authority races:** login vs disable; owner manifest mismatch vs seed; two simultaneous grant attempts; grant revoke vs request; duplicate migration/seed execution. Outcome is serialized, idempotent and auditable, and never restores a revoked grant.
11. **Unclassified identities:** existing user without exactly one explicit owner, conflicting owner, or binding with no recognized council fails closed and does not silently map from email/home fields/context choice. Migration preflight identifies the blocking IDs without exposing credential material.
12. **Residual privileged boundary:** app-role and direct SQL negatives prove only the tested role/path. Tests/documentation identify the `BYPASSRLS` runtime, database owner, superuser, DDL/trigger disablement and deployment actors as trusted residual paths; do not claim protection against a compromised host/runtime or production council isolation.

### Rollback and recovery

Migration is forward-only for authority: owner assignment and Beta grant retirement history cannot be deleted or reversed by rerunning the old seed. Seed rerun must neither reactivate the Beta grant nor alter owner. Do not deploy old code against a database after enforcement because it can bypass the session owner column/application assertions; rollback of app code is blocked. If code/schema release fails, keep API admission/operations disabled until a compatible forward repair preserves owner map, session boundaries and grant revocations. A whole-database restore from before a revocation cannot be proven safe by this slice alone: external immutable revocation evidence/reconciliation is a residual recovery requirement. This contract does not authorize a restore procedure.

### Residual limitations

- Existing `users.role` remains user-level; this first slice enforces **council ownership only**, not Q02's complete per-context role/capability model. Do not add grants of different roles in different contexts or claim Q02 complete.
- Global email uniqueness remains; duplicate-email council accounts, council-qualified lookup and MFA/SSO audience implementation need a separate reviewed slice. Do not use shared email or IdP subject to merge principals.
- Q01 delegation/actions, Q04 real-world proofing/custodian loss/replacement, Q05 structural workflows and Q07 approval framework remain unimplemented.
- The API runtime has `BYPASSRLS`, broad control-table access and privileged helpers. This slice can enforce ownership with immutable DB state, constrained writers and checks in tested paths; it cannot prove isolation against compromise of runtime, database owner/superuser, deployment host, migration credentials, or disabled triggers. Q08 dedicated council runtime/data credentials/topology remains a separate G03 design.
- D03 Q06 has retained-review exceptions: disabled feature must still allow already-authorized in-scope retained request/audit reads, while denying disabled-feature writes and active lookups. A ceiling re-enable must not silently reactivate council feature state. This first slice must preserve current behavior but does not implement Q06.
