## Mock versus implementation and risks

- The inspected production-facing pages call real APIs and render server data, rather than a hard-coded dashboard mock; actual server handlers and database queries are present. Tests mock individual APIs (`enforcementmaps-web/src/features/dispatch/__tests__/IssueInfringementPanel.test.tsx:9`). No runtime, credentials, external service or end-to-end behavior was verified. A loaded page is not evidence that writes, live propagation, permissions, maps or officer interoperability work.
- Location pings deliberately live in server process memory, expire after a configurable five-minute default, and are not audit-grade history (`server/src/modules/officer-status/live-positions.ts:1`, `:22`, `:37`). Multiple workers, restarts or horizontally scaled instances can therefore produce inconsistent live location absent additional shared infrastructure; verify architecture instead of assuming durability. WebSocket tickets and socket subscriptions likewise use process-local state (`server/src/modules/realtime/ws-server.ts:36`, `:62`).
- Last-good snapshot is retained on refresh failure (`DashboardPage.tsx:189`), so users may see stale information; provide explicit freshness/error behavior in any rebuild. Wildcard refetches may amplify traffic under load (`:494`). Geographic self-pin uses browser geolocation and is local, whereas officer/token/duress sources follow different consent, privacy and expiry rules (`:179`, `:537`, `:556`); do not conflate them. Map failure has a fallback, but map functionality depends on an API key and services (`:715`).
- Maps show assigned-zone data and active Code 21s, whereas recent list includes up to 15 statuses (`ZoneMap.tsx:2918`; `dashboard.routes.ts:217`, `:226`); do not equate map markers with all historical records. Source has map detail fallback when full fetch fails (`ZoneMap.tsx:1307`, `:1317`) and creation has optimistic state, so render success alone is not persistence proof.
- Before implementation, trace complete actual repository, shared schemas, migrations, server registration, permission policies, location consent, retention and deployed configuration. Treat this snapshot as reference evidence, not authoritative design specifications or proof all services are wired. Rebuild in contract-preserving increments and verify with representative field-officer integration, role-scoped data, reconnect/missed events, expiry, error recovery, maps and CODE 1 scenarios.

- `server/src/index.ts:75`–`:106` mounts the actual routers under `/api/auth`, `/api/admin/dashboard`, `/api/admin/patrol-zones`, `/api/admin/officers`, `/api/admin/assignments`, `/api/admin/code21` (including attachments), `/api/admin/officer-status`, `/api/admin/audit`, `/api/officer`, `/api/presence`, `/api/location-pulse`, `/api/markups`, `/api/code1` and `/api/peer-share`. The HTTP server initializes realtime at `server/src/index.ts:122`. `server/src/routes/index.ts:1` is empty, so the entrypoint, not that placeholder, is the evidence for registration. Source wiring does not confirm deployment or a complete DB model.
- Native home combines the active dispatch list with mark-up workflow and routes a selected assignment to No Report, infringement or vehicle form, refreshing after each (`enforcementmaps/tabs/index.tsx:163`, `:177`, `:190`, `:296`). `useActiveDispatches` fetches active items immediately and every 10 seconds; it also uses Code21 socket events and subscribes to the returned zone (`enforcementmaps/hooks/useActiveDispatches.ts:6`, `:28`, `:50`, `:61`). It clears the list on fetch failure (`:17`), a notable field-side visibility caveat. The endpoint returns only the current officer’s `DISPATCHED_ACTIVE`, `IN_PROGRESS`, `ATTENDED`, `PIN_ISSUED` records (`server/src/modules/officer-status/officer.routes.ts:100`). Thus native and dashboard active subsets differ: dashboard active pins exclude `ATTENDED` and `PIN_ISSUED` (`server/src/modules/admin/dashboard.routes.ts:217`), although recent/detail views can still show them. Do not assume field completion remains on the dashboard map.
- Creation spatially routes to received, dispatched-not-active or dispatched-active according to assignment (`server/src/modules/code21/code21.routes.ts:488`, `:514`); officer acknowledgement only updates their own dispatched-active SR to `IN_PROGRESS`, records audit and duty event, and emits `code21.updated` to dashboard and zone (`server/src/modules/officer-status/officer.routes.ts:145`, `:170`, `:179`, `:195`). Native list exposes acknowledge for dispatched-active and vehicle, no-report, and issuance actions for in-progress/attended (`enforcementmaps/components/dispatch/ActiveDispatchList.tsx:120`, `:133`). Shared lifecycle enum includes received, dispatched states, in progress, attended, PIN issued, completed, attended-complete, closed and voided (`shared/schema/enums.ts:31`); server's administrative transition table and lock rules are at `server/src/modules/code21/code21.routes.ts:60`, `:91`. The acknowledgement endpoint is a separate transition path, not fully represented by that administrative transition table.
- Native No Report captures at least three camera photos, each with GPS/time and confirmation (`enforcementmaps/components/dispatch/NoReportWorkflow.tsx:29`, `:57`, `:79`, `:115`); server validates metadata, enforces no prior PIN/final No Report, sets `ATTENDED_COMPLETE`, audits and broadcasts (`server/src/modules/officer-status/officer.routes.ts:247`, `:261`, `:307`, `:326`). The shown handler persists evidence metadata but does not show persisting `imageBase64` in that path (`:293`); separately verify binary storage and retrieval before promising actual photo visibility. Vehicle edits broadcast Code21 updates (`officer.routes.ts:1074`, `:1167`).
- Native infringement is currently a single offence selection and date/time form followed by a PIN-issued alert (`enforcementmaps/components/dispatch/IssueInfringementWorkflow.tsx:49`, `:91`, `:106`, `:118`). Server validates catalogue and time policy, assigned officer and status, generates a PIN, atomically updates the Code21 record to `PIN_ISSUED`, audits, and publishes to dashboard, zone and officer (`server/src/modules/officer-status/officer.routes.ts:1193`, `:1223`, `:1268`, `:1296`, `:1301`, `:1348`, `:1369`). A PIN and issuance metadata on an SR therefore exist in this snapshot; this alone does not establish a standalone infringement model, printable notice or print workflow. Treat these as proposed design, not evidence of an already implemented native flow or printing contract.
- Shared zone co-assignment policy blocks duplicates and allows first officer, same nonempty team, supervisor present, or shift-team present; otherwise it blocks team mismatch (`shared/co-assignment.ts:53`, `:75`, `:83`, `:91`). A dashboard assignment redesign must preserve server enforcement and present conflict messages, not assume any officer can join any zone. These native behaviors are dependencies and integration tests for the dispatch rebuild; they do not require building a new native app.
