## Review, checkpoint and handoff mechanics

1. Builder starts each goal on a clean, named branch/worktree rooted at verified main or explicitly named accepted dependency; record base and stack. Define goal requirements, exact policy sources, dependencies, migration and tests before editing. Preserve independent remediation ownership; do not inherit historical Q3–Q7 gating where owner override makes it parallel.
2. Freeze goal at a committed SHA and tree; capture safe evidence and an audit packet: requirements and DS references, exact base/candidate/diff, commands and complete raw results, test data provenance, CI status, permissions/migration/provider limitations, unresolved decisions. Redact secrets and personal data. Snapshot evidence without changing the audited tree.
3. Launch the builder with `model="gpt-6.1-terra"`, `reasoning_effort="medium"`, `fork_turns="none"` and a portable packet. For each freeze asynchronously launch a **fresh** reviewer with `model="gpt-6-astra"`, `reasoning_effort="low"`, `fork_turns="none"` and no builder conversation or conclusions; supply only frozen packet, source and acceptance criteria. Reviewer inspects the actual candidate and independently verifies claims. Builder may continue only independent ready work on a different branch; never alter the frozen candidate under review. Track `implemented`, `audit_pending`, `changes_required`, `blocked`, `accepted` separately.
4. For every finding, record severity, evidence, decision and owner. Apply fixes to a new immutable candidate, run relevant tests and request fresh reassessment of changed behavior; assess dependencies against the updated accepted SHA. After dependency acceptance, merge/rebase or integrate onto the exact accepted tree, rerun affected and integration checks, freeze a new SHA and revalidate independently; acceptance of an earlier tree does not transfer automatically. Do not treat review launch, PR creation, or self-check as acceptance. If reviewer unavailable or checks fail, record a blocker and continue independent safe work.
5. Checkpoint after meaningful work, test, freeze, review and publication: exact branch/base/candidate/tree, accepted goal and report hashes, dependency SHAs, commands/results, CI, pending decisions, safe next action and dirty state. Preserve versioned records and links in the repository and the project’s established memory workflow, if available, without secrets; verify read-back. Avoid workspace-only paths as durable handoffs. Any memory/tool failure is recorded rather than manufacturing a receipt.
6. Publish focused draft PRs and verify remote head/CI under applicable repository and user authority; do not merge or deploy based on this plan. Release requires distinct authorisation, actual prerequisites and a separately pinned final candidate. The final independent D8 audit uses the integrated exact tree and all goal evidence; a later change invalidates affected acceptance and requires reassessment.
